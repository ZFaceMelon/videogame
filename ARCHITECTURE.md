# Project architecture guide

This document explains **every file** in the videogame project: what it does, how it connects to the rest of the codebase, and what you will likely change as the game grows.

For build instructions, see [README.md](README.md). For a file-by-file explanation of the codebase, see [ARCHITECTURE.md](ARCHITECTURE.md).

---

## Big picture

The project is split into two layers:

| Layer | Language | Folder | Role today | Role long-term |
|-------|----------|--------|------------|----------------|
| **Engine** | C++ | `engine/` | Window, OpenGL, rotating cube | Rendering, physics, animation, input |
| **Game** | OCaml | `game/` | Calls into the engine via FFI | Combat rules, AI, quests, networking |

There are **two ways to run** the same demo:

```
videogame_cxx.exe          game/bin/main.exe
      │                            │
      ▼                            ▼
  main.cpp                   main.ml → Engine.run ()
      │                            │
      └──────────┬─────────────────┘
                 ▼
           engine::run()        (engine.cpp)
                 │
       ┌─────────┴─────────┐
       ▼                   ▼
    GLFW window        Renderer (OpenGL cube)
```

**Runtime flow (each frame):**

1. `engine::run()` polls GLFW for window events.
2. `Renderer::draw(time)` clears the screen, computes a model–view–projection matrix, and draws 36 triangle vertices as a colored cube.
3. `glfwSwapBuffers` presents the frame. Repeat until the window is closed.

## Root files

### `CMakeLists.txt`

The **top-level C++ build script**. Responsibilities:

1. Sets C++20 as the language standard.
2. Downloads **GLFW 3.4** from GitHub using `FetchContent` (requires Git + internet on first configure).
3. Adds the `engine/` subdirectory as a static library target.
4. Builds `videogame_cxx.exe` — a standalone C++ executable for quick testing without OCaml.

This is the entry point for `cmake -B build`.

### `dune-project`

Declares the **OCaml project** name (`videogame`) and minimum Dune version (3.14). Dune reads this file to know how to build everything under `game/`.

### `README.md`

Human-facing guide: prerequisites, build commands, troubleshooting, and suggested next steps.

### `ARCHITECTURE.md`

This file — a map of the codebase.

### `.gitignore`

Tells Git to ignore build artifacts (`build/`, `_build/`, `.exe`, `.lib`, `.obj`, Dune caches, etc.) so only source code is tracked.

## `cmake/` — build helpers

### `cmake/write_link_flags.cmake`

A small CMake **script** (not part of the compiled game). It is invoked automatically after the `engine` library is built.

**What it does:** writes `game/config/link_flags.sexp` with the absolute paths to `engine.lib` and `glfw3.lib` (and `opengl32` on Windows). Dune reads this file so the OCaml executable can link against the C++ engine.

**Why it exists:** Visual Studio produces separate Debug and Release libraries in different folders. Writing link flags at **build time** (instead of configure time) ensures the paths match the configuration you actually built.

## `scripts/` — convenience

### `scripts/build.ps1`

A PowerShell wrapper that runs `cmake -B build` and `cmake --build build --config Release`, then prints the path to `videogame_cxx.exe`.

Optional shortcut — you can run the same `cmake` commands manually.

## `engine/` — C++ game engine

The engine is built as a **static library** named `engine`. Both `videogame_cxx.exe` and the OCaml binary link against it.

### `engine/CMakeLists.txt`

Defines the `engine` static library:

| Source file | Compiled into |
|-------------|---------------|
| `api.cpp` | C FFI wrappers |
| `engine.cpp` | Main loop, GLFW window |
| `gl_loader.cpp` | OpenGL function loading |
| `renderer.cpp` | Shaders, cube geometry, draw calls |

Also links against:

- **glfw** — windowing and OpenGL context
- **opengl32** (Windows) / **OpenGL::GL** (Linux) / Cocoa frameworks (macOS)

The `POST_BUILD` hook runs `write_link_flags.cmake` after each engine build.

---

### Public headers (`engine/include/engine/`)

These headers are safe to include from outside the engine (and from C/OCaml stubs).

#### `engine/include/engine/api.h`

The **C API boundary** — the only surface the OCaml layer (or any other language) should call.

```c
int engine_run(void);           // Start the engine main loop; returns exit code
const char *engine_version(void); // Returns "0.1.0"
```

Functions are wrapped in `extern "C"` so C++ name mangling does not break OCaml's linker.

**You will extend this file** as you add FFI (e.g. `engine_poll_input`, `engine_set_camera`).

#### `engine/include/engine/engine.h`

The **C++ API** — a thin wrapper:

```cpp
namespace engine {
  int run();
}
```

C++ code (like `main.cpp`) includes this instead of `api.h`.

### Engine sources (`engine/src/`)

#### `engine/src/main.cpp`

**C++ entry point** for `videogame_cxx.exe`.

1. Prints `videogame C++ entry point` to the console.
2. Calls `engine::run()` and returns its exit code.

Use this binary when you want to test engine changes without building OCaml.

#### `engine/src/api.cpp`

Implements the C functions declared in `api.h`:

- `engine_run()` → calls `engine::run()`
- `engine_version()` → returns the version string

This is the **bridge** between OCaml's C stubs and the C++ engine.

#### `engine/src/engine.cpp`

The **application main loop**. This is the heart of the engine today.

| Step | What happens |
|------|--------------|
| Init | `glfwInit()`, request OpenGL 3.3 Core profile |
| Window | Create 1280×720 window titled `"videogame"` |
| Context | `glfwMakeContextCurrent`, enable vsync (`glfwSwapInterval(1)`) |
| Renderer | `Renderer::init()` — load GL functions, compile shaders, upload cube mesh |
| Loop | Each frame: `draw(time)` → `glfwSwapBuffers` → `glfwPollEvents` |
| Cleanup | Destroy renderer, window, call `glfwTerminate` |

Also handles **window resize**: a GLFW callback updates `Renderer::resize` so the viewport and aspect ratio stay correct.

**You will grow this file** into a proper engine loop (fixed timestep, input dispatch, scene graph).

#### `engine/src/renderer.h` / `engine/src/renderer.cpp`

The **OpenGL renderer** — everything related to drawing the cube.

**`Renderer` public API:**

| Method | Purpose |
|--------|---------|
| `init()` | Load GL, compile shaders, create VAO/VBO, enable depth test |
| `resize(w, h)` | Set OpenGL viewport |
| `draw(time)` | Clear screen, compute MVP matrix, draw cube |
| `shutdown()` | Reset handles (no GL delete calls yet) |

**Shaders** (embedded as string constants in `renderer.cpp`):

- **Vertex shader** — transforms each vertex by a `uMVP` uniform matrix; passes color to fragment stage.
- **Fragment shader** — outputs the interpolated vertex color.

**Cube mesh** — `kCubeVertices`: 36 vertices (12 triangles × 3 corners), each with:

- 3 floats: position (x, y, z) on a unit cube centered at origin
- 3 floats: RGB color (one color per face)

**Each frame in `draw()`:**

1. `projection` = perspective camera (45° FOV, aspect ratio, near 0.1, far 100)
2. `view` = camera at (0, 1.5, 4) looking at origin
3. `model` = Y-axis rotation based on elapsed time
4. `mvp = projection × view × model` sent to the shader
5. `glDrawArrays(TRIANGLES, 0, 36)`

**You will replace/extend this** with mesh loading, materials, lighting, skeletal animation, etc.

#### `engine/src/gl_loader.h` / `engine/src/gl_loader.cpp`

A **minimal OpenGL loader** — no GLAD or GLEW.

Modern OpenGL functions (like `glCreateShader`) are not exported by `opengl32.dll` on Windows. They must be loaded at runtime via `glfwGetProcAddress("glCreateShader")`.

`gl_loader.cpp`:

1. Defines a function pointer for each GL call the renderer needs (~25 functions).
2. `load()` resolves each pointer once after the GLFW context is current.
3. Thin wrappers (`gl::create_shader`, `gl::draw_arrays`, etc.) call through the pointers.

**Why hand-rolled?** You own every line, there are no hidden dependencies, and you only load what you use. Add new wrappers here as the renderer grows.

#### `engine/src/math.h`

A **header-only 4×4 matrix library** — no GLM dependency.

`Mat4` stores 16 floats in column-major order (what OpenGL expects).

| Function | Purpose |
|----------|---------|
| `identity()` | Identity matrix |
| `perspective(fov, aspect, near, far)` | Projection matrix |
| `look_at(eye, center, up)` | View matrix |
| `rotate_y(radians)` | Model rotation around Y axis |
| `operator*` | Matrix multiplication |

Used by `Renderer::draw` to build the MVP matrix.

**You will extend this** with translation, quaternion rotation, inverse, normal matrix, etc.

## `game/` — OCaml game layer

The OCaml side is thin today: it prints a message and calls into the C++ engine. Long-term, this is where For Honor–style game logic (stance system, attack timing, AI decisions) will live.

### `game/bin/main.ml`

**OCaml entry point.**

1. Prints `videogame OCaml entry point (engine 0.1.0)`.
2. Calls `Engine.run ()` which opens the same cube window as the C++ binary.
3. `exit` with the return code from the engine.

### `game/bin/dune`

Dune build rule for the executable:

- **public_name** `videogame` — the installed binary name
- **libraries** `engine` — the OCaml library defined in `game/lib/`

### `game/lib/engine.ml`

OCaml **bindings** to the C engine API:

```ocaml
external run : unit -> int = "caml_engine_run"
external version : unit -> string = "caml_engine_version"
```

`external` tells OCaml these functions are implemented in C. The string on the right is the C function name in `engine_stub.c`.

**You will add more externals here** as the C API grows (input, game state, etc.).

### `game/lib/engine_stub.c`

**C stubs** that sit between OCaml and the C++ engine.

| OCaml calls | C stub | C++ API |
|-------------|--------|---------|
| `Engine.run ()` | `caml_engine_run` | `engine_run()` |
| `Engine.version ()` | `caml_engine_version` | `engine_version()` |

Includes `<caml/mlvalues.h>` for OCaml's value types. `CAMLprim` marks functions callable from OCaml.

The stub is C (not C++) so Dune can compile it with a C compiler, but it links against the C++ `engine` static library via the C-compatible `api.h` symbols.

### `game/lib/dune`

Dune build rule for the `engine` OCaml library:

| Field | Purpose |
|-------|---------|
| `foreign_stubs` | Compile `engine_stub.c` |
| `c_library_flags` | Add `-I` so the stub can find `engine/api.h` |
| `library_flags` | Include `link_flags.sexp` so the linker finds `engine.lib` and `glfw3.lib` |

### `game/config/link_flags.sexp`

**Auto-generated — do not edit by hand.**

Example contents after a Release build:

```scheme
( -cclib "C:/Users/zanek/videogame/build/engine/Release/engine.lib"
   -cclib "C:/Users/zanek/videogame/build/_deps/glfw-build/src/Release/glfw3.lib"
   -cclib opengl32 )
```

Dune passes these flags to the OCaml linker. Regenerated every time you build the `engine` CMake target.

## How the two languages link together

```
main.ml
  │  Engine.run ()
  ▼
engine.ml          (OCaml externals)
  │  caml_engine_run
  ▼
engine_stub.c      (C stubs, OCaml calling convention)
  │  engine_run()
  ▼
api.cpp            (extern "C" wrapper)
  │  engine::run()
  ▼
engine.cpp         (C++ engine loop)
```

**Build order:**

1. `cmake --build build` → compiles `engine.lib`, writes `link_flags.sexp`
2. `dune build game/bin/main.exe` → compiles OCaml + stub, links against `engine.lib`

## External dependency: GLFW

GLFW is **not** a file in your repo. CMake downloads it on first configure into `build/_deps/glfw-src/`.

GLFW provides:

- Cross-platform window creation
- OpenGL context management
- Input polling (`glfwPollEvents`)
- Time (`glfwGetTime`)
- `glfwGetProcAddress` for loading OpenGL functions

You interact with GLFW only in `engine.cpp`. The renderer never includes GLFW headers directly (except `gl_loader` for `glfwGetProcAddress`).
